# mylibrary の設計思想

この文書は、`mylibrary` の現在の実装を説明するためだけのものではない。
将来の実装や設計案を評価するための基準を記録するものである。

## 想定する利用者と文書

このライブラリは、主として自分が数学文書を書くために使う。
対象は論文、研究ノート、講義ノートのいずれか一つに限定しない。

## 想定する使い方

特定の LaTeX エンジンだけに依存するライブラリにはしない。
エンジンに依存しない共通基盤を用意し、その上で LuaLaTeX、XeLaTeX、その他のエンジンを必要に応じて使い分けられる構成を目指す。

論文などを投稿するときは、style ファイル、`latexmkrc`、フォントなど、コンパイルに必要なものを文書ごとに self-contained な形で整理して提出できるようにする。

## 利用者の執筆体験

最も重要な利用例は、クラスを指定するだけで、通常の執筆に必要なパッケージとマクロのほとんどが揃っている状態である。
文書を書き始めた後に、必要な機能を見つけるたびに個別の `\usepackage{...}` を追加することを、基本的な利用方法にしない。

同時に、文書を作り始めた後で変更したくなる設定を変更できることも重視する。
対象には、定理や式の番号付け、ヘッダー・フッターの有無などが含まれる。

クラスや内部で使っている環境によって、執筆時の記法を変えない。
例えば、`amsthm` を使う場合と tcolorbox を使う場合とで、

```tex
\begin{definition}[タイトル]
\label{def:sample}
...
\end{definition}
```

の書き方を変えない。定理環境の内部実装が異なっても、利用者が書く文書の記法は可能な限り統一する。

エンジン依存の操作や機能も、完全に無くすことはできないとしても、利用者が意識する必要を可能な限り減らす。

## クラスと執筆環境の責務

クラスは、文書の構造、標準的な体裁、定理環境、共通パッケージとマクロの提供を担当する。
一方、ワークスペースごとのコンパイルエンジンの選択は、プロジェクト側または VS Code 側で扱う。
具体的には、`latexmkrc`、toolchain、recipe、workspace 設定などを用いる。

この分離を採るなら、クラス名に `-xe` や `-lua` を含める必要は必ずしもない。
同じ `.tex` ファイルを、ワークスペース側の設定だけ変えて異なるエンジンでコンパイルできる構成を優先する。
ただし、エンジン差をクラスから完全に隠せない場合に、エンジン別クラスを設けるかどうかは未決定である。

新しい文書の作成時に最小限の `.tex` 内容を自動生成する機能も、クラスの責務とは分ける。
VS Code のテンプレートやスニペット、またはプロジェクト内のテンプレートファイルによって、例えば次の内容を生成できるようにする。

```tex
\documentclass[option]{class}

\title{title}
\date{\today}
\author{author}

\begin{document}

\maketitle

\end{document}
```

テンプレートはクラスの利用例を示す入口であり、クラス内部の実装とは独立に変更できるものとする。

ここでいう「後から変更できる」とは、同じ文書の一部で設定を切り替えて異なる見た目を混在させるという意味ではない。
執筆中に設定を変更し、再コンパイルしたときには文書全体に一貫して反映されるという意味である。
基本的に、一つの文書の見た目や番号付けは統一されていてよい。

## 代表的な執筆場面

次の既存文書を、新しい仕組みが想定すべき執筆場面の例として参照する。
ただし、既存のクラス名、環境名、引数形式、ファイル構成を新しい仕組みが維持する必要はない。

### 数学の研究ノート

`soyuri-morphism` のような日本語の研究ノートでは、クラスを指定するだけで、少なくとも次の機能が利用できることが望ましい。

- 定義、補題、命題、例、注意
- 証明と手動の QED 記号
- 数式環境、数式参照
- 箇条書き
- TikZ による図や可換図式
- 数学記号と頻繁に使う演算子

本文では、定理環境の内部実装や読み込まれたパッケージを意識せずに、定義・補題・証明を書けることを重視する。

### 日本語を含む数学の論文・Survey

`cusp_eq` のような文書では、日本語と英語の数学本文、TikZ による図、可換図式、数学フォント、定理環境、式番号の設定、文書固有の数学記号を同時に扱う。

この種の文書では、クラス指定だけで共通的な機能を利用でき、フォントや文書全体の体裁を必要に応じて変更できることが望ましい。
一方、論文固有の記号や定義まで共通クラスに無条件で組み込むことを意味しない。

これらは既存文書の仕様を保存するためのテストではなく、新しい環境が提供すべき利用体験を考えるための例である。

## 文書ワークスペースの方針

### notes

`notes` は、複数のノートを含む一つの共有ワークスペースとして扱う。
標準のコンパイルエンジンは LuaLaTeX とする。
必要に応じて、同じワークスペースの `.vscode/` に XeLaTeX 用の設定や recipe を置き、別のエンジンにも対応できるようにする。
各ノートに個別の `latexmkrc` や `.vscode/` を置くことは、標準の運用にしない。

### papers

`papers` は、論文ごとに独立したワークスペースとして扱う。
一つの論文のワークスペース内で、クラス、パッケージ、マクロ、フォント、`latexmkrc`、VS Code 設定など、コンパイルに必要なものを管理する。
投稿時には、そのワークスペースだけでコンパイルでき、必要なファイルをそのまま提出できる self-contained な状態にする。

ここでいう self-contained とは、開発時に共有ライブラリを参照しないという意味ではない。
投稿用に必要なファイルを論文のワークスペースへ確定した形で含め、共有ライブラリの将来の変更に左右されずにコンパイルできる状態を意味する。

科研費申請書のように指定テンプレートと指定エンジンに従う文書は、この方針の対象となる一般的な数学文書とは別系統のワークスペースとして扱う。

## 基本原則

### シンプルであること

必要性が明確でない機能や抽象化を先回りして追加しない。
数式番号や定理番号の細かな仕様にも、必要性の検討なしに過剰な労力をかけない。

### 拡張性を持たせること

将来の機能追加や見た目の変更を妨げない構成にする。
ただし、拡張性を理由に現時点で不要な複雑な抽象化を導入しない。

### 汎用的、universal であること

特定の文書、言語、エンジン、フォント、文書クラスに必要以上に依存しない。
エンジンに依存しない部分と、LuaLaTeX・XeLaTeX などに依存する部分を分離する。

ここでいう汎用性は、すべての TeX エンジンを対象にすることを意味しない。
新しい日本語文書の対応エンジンは、基本的に LuaLaTeX と XeLaTeX とする。
その他のエンジンで日本語文書を作成することは、現時点では対応範囲に含めない。
共通化するのは、対応対象としたエンジンの違いを、利用者の執筆時の記法から可能な限り隠すことである。

この三原則の間に優先順位があるとは、現時点では決めていない。
具体的な提案では、どの原則に基づく判断なのかを明示する。

なお、ここでいうシンプルさは、読み込む機能を最小限にすることだけを意味しない。
利用者がクラス指定だけで執筆を始められることも、重要なシンプルさである。

## 構成に関する考え方

共通基盤、エンジン固有の設定、文書クラス、定理・証明環境、見た目に関する設定は、同じ責務として扱わない。
ただし、これは責務を分離するという設計原則であり、現在のディレクトリ名やファイル配置を永久に固定するという意味ではない。

tcolorbox による定理環境・証明環境は引き継ぐ。
一方、`\hspace` などによる細かな位置調整や、構造的に不自然な実装は刷新する。

定理環境の内部実装が `amsthm` か tcolorbox かにかかわらず、利用者側の環境名、引数、`\label` などの記法は可能な限り統一する。

現在ある `.cls` の仕様に、新しく設計する仕組みを合わせる必要はない。
既存文書の保持や既存クラスとの互換性は、この新しい仕組みの目的ではない。
既存のクラスや文書は、必要なら参照・比較の対象にはするが、新しい仕様を決める制約にはしない。
新しい仕組みの目的は、これから新しい環境で文書をより快適に作成できるようにすることである。

## 採用済みの設計判断

### 定理環境の実装を無理に一つへ統合しない

**状態：採用済み**

新しい環境で `amsthm` を使う部分と、tcolorbox を使う部分は、それぞれの目的に応じて設計する。
現在ある `normal.cls` やその他の `.cls` の仕様に合わせることは要求しない。

両者で文書側の環境名や使用方法を揃えられる部分は揃えるが、内部実装や見た目まで無理に共通化しない。
`amsthm` と tcolorbox は、それぞれの標準的な仕組みを利用できる形を保つ。

この判断は、利用者側の記法まで別々にすることを意味しない。
内部実装は分けても、執筆時のインターフェースは可能な限り共通にする。

## 未決定の設計事項

番号付けやヘッダー・フッターなどの可変な設定を、

- クラスのオプションで切り替えるのか
- 必要なバリエーションごとにクラスを分けるのか

は、まだ決めていない。
この選択は、利用者の執筆体験と、設定の変更しやすさを基準に決める。
現時点でどちらかを採用済みとは扱わない。

## 目指さないこと

ここで挙げる事項は「永久に実装しない」という意味ではなく、必要性が示されるまでは優先しないという意味である。

- 必要性が明確でない機能の先回りした実装
- 数式番号・定理番号の細部のための過剰な複雑化
- 見た目の微調整だけを目的とした不自然な実装
- エンジン固有の機能を共通基盤へ無条件に持ち込むこと

## 文書の更新規則

提案・検討中の案を、採用済みの事項として書かない。
設計判断を変更するときは、以前の判断を黙って削除せず、変更理由を記録する。
過去のログで確認できない要件や理由は、確認済みの事実と区別して記載する。
